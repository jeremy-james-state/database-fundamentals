Normalization splits tables so each fact has one home.

Denormalization copies a fact on purpose so a frequent query can avoid a join.

It is a last-ditch optimization after you have evidence, not a shortcut past design.

A clean schema can still make a dashboard join five tables and take seconds.

Users feel the seconds, not the purity.

The responsible version has two steps.

First, watch which queries run often and which of them join more than two tables.

Guessing is how you duplicate the wrong column.

Second, copy a column into a table that already participates, so the hot query joins less, or not at all.

A music catalog might store artist_name on a track row that already has album_id, if top tracks by famous artists are the hot path and always needed the name.

You now update artist_name in two places, or you accept a nightly rebuild, or you use a trigger to copy.

That extra write is the cost.

The extra consistency work is the cost.

You created an anomaly and called it speed.

Document the source of truth: artists.name is canonical, tracks.artist_name is a cache.

If they disagree, the canonical wins, and the cache is rebuilt.
