An index is a lookup structure beside the table, like a book's table of contents, pointing at where a row lives.

Without one, a search can walk every row.

That is a sequential scan, and it gets slower as the table grows.

With a useful index, the engine jumps closer to the matches.

A B-tree index keeps keys in a balanced tree so every lookup is about the same depth.

Equality and ranges both like B-trees: customer_id equals seven, created_at greater than a date.

ORDER BY on an indexed column can avoid a separate sort.

The tree is a copy of the key values plus pointers.

Insert, update, and delete must maintain the tree, so writes get a little slower.

That is the tax you pay for faster reads.

Create an index on columns you filter and join, not on every column because it felt complete.

Each extra index is another structure to store and update.

A composite index on (city, created_at) helps a filter that uses city, or city and created_at, left to right.

It may not help a filter that only uses created_at, depending on the engine.
