Think of a family tree of **ranges**, not people. The **root** (parent) sends you left or right. **Children** narrow the range. **Leaves** hold the actual indexed values (and pointers to rows).

## How a B-tree search works

To find `Cars` in a title index:

1. Start at the root. Titles before *M* go one way; later titles go the other.
2. At each child, narrow again (like binary search on a sorted list, but branching more than two ways).
3. Stop at a **leaf** that contains `Cars` (or shows it is missing).

You do not walk every title in the table. You walk a short path down the tree.

That is why an [index](/concepts/indexes) beats a scan on a large table: the search algorithm does less work as the table grows.

## Why databases use B-trees

Sorted structure + branching keeps lookups predictable. Inserts and deletes can rebalance the tree so it stays shallow.

You give up some space: the tree is stored next to the table.

## When this matters

- **You are reading a query plan**: “SEARCH … USING INDEX” means a tree walk, not a full scan
- **Skip deep implementation detail when**: you only need to choose which columns to index; the DBMS owns the tree
