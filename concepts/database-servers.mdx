SQLite opens a file. MySQL and PostgreSQL listen on a host and port. You connect with credentials, pick a database, then run SQL.

## Connection and credentials

A **connection** is the session between your client and the server. Each request on that session carries a **user identity**. The database uses that identity to apply [GRANT](/reference/grant) privileges and row policies — not an anonymous client.

How the identity arrives depends on the stack:

| Stack | What carries identity | What the database sees |
| --- | --- | --- |
| **PostgreSQL / MySQL (direct)** | Connection string role and password (or certificate), or a backend that opens the session then sets session context | A database role such as `analyst`; statements run as that role |
| **Supabase** | The signed-in user’s JWT plus the project’s publishable (anon) key on the client request | Postgres role `authenticated` (or `anon`), with `auth.uid()` from the JWT for Row Level Security |

In raw Postgres you often connect as a specific role in the connection string. An application backend may instead connect as a shared role and set session variables or `SET ROLE` so the request still has a clear subject for privileges and policies.

In Supabase the browser does not open a Postgres password login for each end user. The request presents the user’s access token and the publishable project key; the API maps that to a database session where grants and RLS run under that identity.

| Step | What happens |
| --- | --- |
| Connect / request | Client opens a session (or sends a request that becomes one) |
| Authenticate | Credentials or token prove **who** is on the request |
| Authorize | [GRANT](/reference/grant), roles, and row policies apply to that identity |
| Query | SQL runs under those privileges |

SQLite usually has no server login. Access is mostly file permissions on the `.db` file, not a per-statement account identity.

See [Connect to PostgreSQL](/how-to/connect-to-postgresql) and [Connect to MySQL](/how-to/connect-to-mysql) for direct client steps. See [Authentication and authorization](/concepts/authentication-and-authorization) for membership, roles, and RLS on top of session identity.

## How server DBMS products compare

| | **SQLite** | **MySQL** | **PostgreSQL** |
| --- | --- | --- | --- |
| Shape | Embedded library + `.db` file | Server process | Server process |
| Clients | Your app / `sqlite3` | `mysql` client, apps | `psql` client, apps |
| Users | File permissions | Accounts + [GRANT](/reference/grant) | Accounts + privileges |
| Identifiers | `"name"` or bare | `name` (backticks) | `"name"` or bare |
| Types | Affinities ([storage classes](/concepts/storage-classes)) | Strict types ([server types](/concepts/server-types)) | Strict types |
| Auto ids | `INTEGER PRIMARY KEY` | `AUTO_INCREMENT` | `SERIAL` / `GENERATED` |
| Scaling tools | One file | Replication, sharding patterns | Replication, sharding patterns |

MySQL and Postgres both support richer types, stored routines, and multi-user access. They cost more to run and operate than SQLite.

## Authentication, authorization, and integrity

These layers answer different questions during a database write:

| Layer | Question | Common mechanisms |
| --- | --- | --- |
| **Authentication** | Who is connecting? | Account and password, certificate, token, or operating-system identity |
| **Authorization** | What may that identity do? | Roles, ownership, [GRANT](/reference/grant), and [REVOKE](/reference/revoke) |
| **Data integrity** | Is the resulting data valid? | [Primary keys, foreign keys, `NOT NULL`, `UNIQUE`, and `CHECK`](/concepts/constraints) |
| **Transaction control** | Do related changes become permanent together? | [`BEGIN`, `COMMIT`, and `ROLLBACK`](/concepts/transactions) |

A successful login does not authorize every action. Permission to `INSERT` does not guarantee that an inserted row is valid. The server first identifies the account, then checks its privileges, then applies constraints to the proposed data. A transaction controls whether a group of accepted statements commits as one unit.

Use the layers together:

1. Authenticate the application or person.
2. Grant only the operations and objects they need.
3. Enforce business invariants with constraints, regardless of which authorized client writes.
4. Wrap multi-step changes in a transaction.

See [Authentication and authorization](/concepts/authentication-and-authorization) for a tenant membership, role-permission, and RLS example.

## Why teams move to a server

Many writers, network clients, and features such as [replication](/concepts/replication) need a server. SQLite stays excellent for local apps, tests, and modest load.

## When to use which

- **SQLite**: one machine, simple deploy, embedded app data
- **MySQL or PostgreSQL**: many users, stricter types, horizontal scale
- **Skip a server when**: a single SQLite file still meets your needs
