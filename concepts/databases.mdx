Spreadsheets hold a grid. A database holds that grid — and often many grids — so many programs can create, read, update, and delete the same data at scale.

## Where the data lives

The **database** is the store itself. How you reach it depends on the product:

| | SQLite | MySQL / PostgreSQL |
| --- | --- | --- |
| Where the data lives | A **path** to a file, or `:memory:` | A named database on a host |
| You connect with | That path | Host, credentials, database name |

### Create a database

| Product | How you create it |
| --- | --- |
| SQLite | Open a path with `sqlite3 books.db`. No `CREATE DATABASE`. Missing file → empty database. See [Open a SQLite database](/how-to/open-a-database). |
| MySQL / PostgreSQL | Connect to the server, then run `CREATE DATABASE name;` and `USE` / connect to that name. See the [scaling tutorial](/tutorials/scale-with-servers). |

The suffix (`.db`, `.sqlite`) is convention only: SQLite opens the file when the contents are a SQLite database (it starts with `SQLite format 3`).

On a [database server](/concepts/database-servers), one host can hold several named databases. You pick which database to use after you connect. An empty database still needs [tables](/concepts/tables) before you store rows.

## Database management system

A **database management system** (DBMS) is the software between that store and you. You send statements to the DBMS; you do not edit storage files by hand.

| Term | Meaning |
| --- | --- |
| Database | Where the data lives |
| DBMS | The program that manages it |

Everyday speech often says “database” for both. Keep the split when you choose tools or debug a connection: the file or named store is the database; SQLite, MySQL, and PostgreSQL are DBMS products that manage it.

## Relational databases

A **relational database** stores data in [tables](/concepts/tables) related by [keys](/concepts/keys). Each table is a set of rows under one [schema](/concepts/schemas). Rows in one table correspond to rows in another through [relationships](/concepts/relationships) — for example `books.author_id` matching `authors.author_id`.

That shape is why [SQL](/concepts/sql) starts here. SQL assumes fixed columns, set-based work over rows, and joins across tables. When people say “learn SQL,” they mean talking to a relational DBMS: create tables, insert rows, filter with `WHERE`, join related tables, and enforce [constraints](/concepts/constraints).

This course and site use relational databases throughout. The examples begin with SQLite, then move to MySQL and PostgreSQL on a server.

## Other database types

Not every database is relational. Other products store documents, key–value pairs, graphs, or other shapes, and they often use a different query language than SQL.

Those systems matter in production. This site does not cover them. When a page says **database**, **table**, or **SQL**, it means the relational path above.
