In database design, a [table](/concepts/tables) often **represents an entity** — the kind of thing you store facts about: customer, product, book. The table is the SQL structure; the entity is what you named in the design. Same name in both places is common (`books` entity → `books` table); they are still two layers.

| Entity (conceptual) | Table (physical) | Example |
| --- | --- | --- |
| Entity name | Table name | `books` |
| [Attributes](/concepts/attributes) | Columns | `title`, `year`, `isbn` |
| Instances | Rows | one book |
| Attribute on an instance | [Cell](/concepts/tables#cells) value | `1979` |
| Unique identifier | [Primary key](/concepts/keys) | `book_id` |

**One table = one entity**, or one [relationship](/concepts/relationships) between entities. Point across tables with [keys](/concepts/keys). [Normalization](/concepts/normalization) is the systematic version of that split.

Facts about the entity are [attributes](/concepts/attributes) — each becomes a typed column. Do not park a whole second kind of thing as a column when it needs its own identity; that is another entity.

## Instances

An **instance** is one occurrence of the entity — *The Left Hand of Darkness* is one book. In the table, each instance is a [row](/concepts/tables#rows). The value of an attribute on that instance sits in a [cell](/concepts/tables#cells).

## From requirement to model

Choose the smallest structure that preserves identity, multiplicity, history, and the rules that must remain true:

| Rule of thumb | Model it as | Example |
| --- | --- | --- |
| One fact describing something | **Column** | `people.birth_date` |
| Own identity, details, or lifecycle | **Table** | `products`: `product_id`, `name`, `current_price` |
| Many related items | **Multiple rows**, usually in a related table | `addresses`: one row per address, linked by `person_id` |
| Relationship or event has details | **Table with foreign keys and detail columns** | `purchases`: `person_id`, `product_id`, `quantity`, `price_paid`, `purchased_at` |
| Preserve a fact as it was | **Snapshot columns** on the relevant record; a history table if you need every change | Copy the agreed unit price into `purchases.price_paid` |
| Must always be true | **Constraint** on columns or tables | Foreign key on `product_id`; `CHECK (quantity > 0)` |

A product’s current price and a purchase’s agreed price answer different questions. Keep `products.current_price` for the value now. Store `purchases.price_paid` so later product updates do not rewrite history.

See [Attributes](/concepts/attributes), [Relationships](/concepts/relationships), and [Constraints](/concepts/constraints) for each decision in detail.
