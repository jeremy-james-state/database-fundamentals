**Capacity** is how much work the system can take: more users, more rows, more queries per second. You scale **up** when load grows. You can also scale **down** when you no longer need the extra machines.

## How scaling works

| Approach | What you change | Picture |
| --- | --- | --- |
| **Vertical** | One server gets more CPU, RAM, or disk | A taller single machine |
| **Horizontal** | You add more servers and share the work | Several machines side by side |

SQLite is an **embedded** library in your app. [MySQL](/concepts/database-servers) and [PostgreSQL](/concepts/database-servers) are **database servers**: clients connect over the network, with users, privileges, and features built for many connections.

Horizontal work often uses [replication](/concepts/replication) (copies) and [sharding](/concepts/sharding) (splits).

## Why databases scale this way

One machine has a ceiling. Vertical scaling hits that ceiling. Horizontal scaling buys more machines, but you must keep copies consistent and decide who accepts writes.

## When to use each

- **Vertical**: one server still fits; you want a simpler ops story
- **Horizontal**: one box cannot hold the data or the query load
- **Skip complex topologies when**: SQLite on one machine still meets the load
