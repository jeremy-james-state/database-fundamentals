You decide it before you load rows. Links between tables usually go through [keys](/concepts/keys) and [constraints](/concepts/constraints). Each [table](/concepts/tables) stores one [entity](/concepts/entities) (or one [relationship](/concepts/relationships) between entities). Each column is one [attribute](/concepts/attributes) with a [storage class](/concepts/storage-classes) (or [server type](/concepts/server-types)) the DBMS will try to store.

## Database schema

A **database schema** is the whole set of tables and how they link. When people say “the schema,” they usually mean this — the map of the database.

## Table schema

A **table schema** is one table’s definition: columns, types, and rules for that table. In SQL that is typically a `CREATE TABLE` statement.

## `.schema`

In SQLite, `.schema` prints the `CREATE TABLE` (and related) statements that built the structure. That listing *is* the schema in SQL form.

```text
sqlite> .schema
sqlite> .schema books
```

The SQL equivalent reads the catalog:

```sql
SELECT sql
FROM sqlite_master
WHERE type = 'table';
```

Keep a `schema.sql` file if you want to rebuild the empty structure: edit the file, then [apply it](/how-to/apply-a-schema-file). For incremental change on a live database, use [migrations](/concepts/migrations) — versioned SQL files plus a history of which versions were applied.

## Schema design checklist

| Rule | Concrete choice |
| --- | --- |
| **Define what one row represents** | Separate one order from one order item; use `orders` and `order_items` |
| **Give each row stable identity** | Use a [primary key](/concepts/keys#primary-key); do not identify a row only by a changeable name |
| **Store each current fact in one authoritative place** | Keep the company name in `companies`; reference `company_id` elsewhere |
| **Model repeatable things as rows** | Store order items as rows; avoid `product_1`, `product_2`, and `product_3` columns |
| **Define business uniqueness** | Make `order_reference` `UNIQUE` even when `order_id` is already the primary key |
| **Create only real relationships** | Add [foreign keys](/concepts/keys#foreign-key) for genuine dependencies; a standalone table is valid when no dependency exists |

These choices work together. The primary key supplies technical identity; a `UNIQUE` constraint protects a separate business identifier. [Normalization](/concepts/normalization) gives each current fact one authoritative home, while related rows preserve values that can repeat.

## Why

Without a schema you only see values. You cannot tell whether `amount` is text or a number, or whether `book_id` on ratings must match `books`.

## When

- **Before data**: decide tables and keys, then insert
- **To inspect**: `.schema` or `sqlite_master` when you did not write the `CREATE`
- **Skip inventing a new schema when**: one [table](/concepts/tables) already holds similar items
