`.schema` prints the `CREATE TABLE` statements that built it. That listing *is* the schema in SQL form.

## How a schema works

You design the schema before you load rows. Each table names an entity. Each column names one attribute and a [storage class](/concepts/storage-classes) the DBMS will try to store.

A **database schema** is the whole set of tables. A **table schema** is one `CREATE TABLE`.

SQLite can show you either:

```text
sqlite> .schema
sqlite> .schema stations
```

The SQL equivalent reads the catalog:

```sql
SELECT sql
FROM sqlite_master
WHERE type = 'table';
```

## Why databases use a schema

Without it you only see values. You cannot tell whether `amount` is text or a number, or whether `station_id` must match `stations`.

Keeping the schema in a `schema.sql` file lets you rebuild the empty structure: edit the file, then [apply it](/how-to/apply-a-schema-file).

## When to use a schema

- **Before data**: decide tables and keys, then insert
- **To inspect**: `.schema` or `sqlite_master` when you did not write the `CREATE`
- **Skip inventing a new schema when**: one [table](/concepts/tables) already holds similar items

## Related ideas

[Normalization](/concepts/normalization) decides how many tables. [Keys](/concepts/keys) connect them. [Constraints](/concepts/constraints) reject bad rows. [CREATE TABLE](/reference/create-table) writes the schema down.

## Common mix-ups

- **Schema vs data**: `CREATE TABLE` is structure. Rows are data. `.schema` does not print the rows.
- **`.schema` vs SQL**: `.schema` is a SQLite command. `SELECT sql FROM sqlite_master` is SQL.
