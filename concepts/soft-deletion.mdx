---
title: "Soft deletion"
description: "Soft deletion marks a row as gone without removing it. A deleted or archived column holds that mark."
keywords: ["CS50"]
---

A hard [DELETE](/reference/delete) drops the row. Recovery means a backup. A **soft delete** [UPDATE](/reference/update)s a flag such as `deleted` from `0` to `1`. Queries that should see “live” rows add `WHERE deleted != 1`.

## How soft deletion works

Add the column with [ALTER TABLE](/reference/alter-table):

```sql
ALTER TABLE collections
ADD COLUMN deleted INTEGER DEFAULT 0;
```

Mark one row:

```sql
UPDATE collections
SET deleted = 1
WHERE title = 'Farmers Working at Dawn';
```

The row is still there. `SELECT * FROM collections WHERE deleted != 1` hides it.

## Why databases use soft deletion

You keep a history of items that left the collection. You can undo the flag.

You take on a duty: every everyday `SELECT` must filter the flag, or “deleted” rows leak back into results. For personal data, hiding a row is not the same as erasing it. Laws such as GDPR’s right to be forgotten may require a real `DELETE`.

## When to use soft deletion

- **You may need the row later**: inventory, audit, undo
- **Skip it when**: the owner asked you to erase the data, or the row has no reason to exist

## Related ideas

The flag is an ordinary column, often with a [DEFAULT](/reference/default) of `0`. Everyday queries add `WHERE deleted != 1`. A [view](/concepts/views) of live rows (`WHERE deleted = 0`) plus an [INSTEAD OF DELETE](/how-to/write-through-a-view) trigger can soft-delete when someone deletes from the view.

## Common mix-ups

- **Soft vs hard**: `UPDATE … SET deleted = 1` keeps the row. `DELETE FROM` does not.
- **Default 0**: new rows are live unless you set the flag.
