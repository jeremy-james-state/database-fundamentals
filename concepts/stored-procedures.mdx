---
title: "Stored procedures"
description: "A stored procedure is named SQL saved in the server that you run with CALL."
---

Unlike a [view](/concepts/views), a procedure can run multiple statements, take parameters, and use `IF` / `ELSE`. It lives in the database so many clients share the same logic.

## How a stored procedure works

```sql
CREATE PROCEDURE credit_account(IN account_id INT, IN amount INT)
BEGIN
  UPDATE accounts
  SET balance = balance + amount
  WHERE id = account_id;
END;
```

```sql
CALL credit_account(1, 10);
```

`USE some_database;` selects which database on the server holds the procedure. One procedure may `CALL` another. Parameters pass inputs (and sometimes outputs) without pasting values into ad hoc SQL strings.

## Why databases use procedures

Automation and a single place for a multi-step rule. You give up some portability: dialects differ, and logic in the database is harder to version than app code for some teams.

## When to use a procedure

- **The same multi-step write from many clients**
- **Skip it when**: a view (read-only shape) or app code is clearer

## Related ideas

[Triggers](/concepts/triggers) fire on row changes. Procedures run when you `CALL` them. Prefer [prepared statements](/concepts/sql-injection) for user input either way.

## Common mix-ups

- **Procedure vs view**: views are queried like tables. Procedures are executed.
- **Procedure vs trigger**: you call a procedure; a trigger runs from an `INSERT`/`UPDATE`/`DELETE`
