A **table** stores a set of items. Each **row** is one item. Each **column** is one attribute of that item.

You already know this shape from paper lists and spreadsheets. Databases use the same grid: items down, attributes across.

## How a table works

Take a `books` table.

- One row is one book.
- `title` is an attribute of that book.
- `author` is another attribute.
- `year` is another.

Two books never share a row. Two attributes never share a column. If you need a third fact about each book, you add a column. If you add a book, you add a row.

## Why databases use tables

A table makes each fact sit in a known place. You can ask for every title, or every book from `2023`, without reading a paragraph of prose.

The same idea is old. Ledgers used rows and columns long before software. Spreadsheets and databases both inherited that grid.

## When to use a table

- **A set of similar items**: books, orders, customers
- **The same attributes on every item**: every book has a title and an author
- **Skip it when**: you only have one unstructured blob of text with no repeating attributes

## Related ideas

A table lives inside a [database](/concepts/databases). You read its rows with [SQL](/concepts/sql). See [query a table](/tutorials/query-a-table) to select rows.

## Common mix-ups

- **Table vs database**: the table is one grid. The database is the whole collection of tables and the system around them.
- **Row vs column**: the row is the item. The column is one kind of fact about every item.
